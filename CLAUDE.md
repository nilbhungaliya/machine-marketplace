## Project Overview

**Machine Parts & Machinery Marketplace** (working name "MPM") is a mobile-first B2B app where Indian businesses buy,
sell and source machine parts, spare parts and machinery — and rent machinery out — plus a web admin panel that runs
the marketplace.

**Core loop:** seller lists a part or machine → buyers find it (search, filters, location, left/right matching) or are
alerted through a part request → enquiry → offer and counteroffer in chat → deal agreed → marked sold / rented →
both sides review.

**What makes it different:** **Left / Right / Pair** part matching (a business with one side of a part finds the
other), **part requests with availability alerts**, structured specs and machine compatibility per category, and a
shared deal record even when payment happens outside the platform.

**Surfaces:**
- **User App** (`apps/user-app`, React Native / Expo) — one account both buys and sells
- **Admin Panel** (`apps/admin`, Next.js 14) — role-based; every action audit-logged
- **API** (`apps/api`, Fastify) — shared by both

The product scope is `docs/Machine Parts Marketplace Product Scope.pdf`; a text extract you can read is
`docs/product-scope.txt`. Modules carry IDs there — **U1–U4** user flows, **F1–F9** app features, **A1–A6** admin
panel — reference them in plans, code comments and commits.

The **full feature specification** is `docs/product-scope.md`: modules **M1–M20** (app) and **AD1–AD7** (admin), each with
workflow, fields, phase (MVP / P2 / P3), the PDF IDs it covers and competitor inspiration; the research behind it is in
`docs/research/`. The design for client review is `docs/mockups/user-app-mockup.html` (generated by
`docs/mockups/src/build.mjs`; see `docs/mockups/README.md`) and is the UI brief.

**Lineage:** the base (monorepo layout, auth, plugins, sockets, jobs runner, admin kit, app kit, i18n, deploy kit)
was ported from the Textile Stock Marketplace project (`C:\Users\Dell\Desktop\textile stock marketplace`), which itself
took its base from ORA. When a shared foundation piece is needed (media uploads, outbox events, search, notifications),
look at how textile built it first — same stack, same conventions.

### Local database

Dev and tests run on Docker (`infra/docker-compose.yml`, Postgres 18 + PostGIS):
- `mpm` (dev) is `DATABASE_URL`; `mpm_test` (tests only) is `TEST_DATABASE_URL`; Redis DB 0 is dev, DB 1 is tests (`TEST_REDIS_URL`).
- `apps/api/vitest.config.ts` swaps the `TEST_*` URLs in and **refuses to run** without `TEST_DATABASE_URL` + `TEST_REDIS_URL`
  or when the test database's name doesn't end in `_test`, so a test run never touches dev data. It also raises the global rate limit (`RATE_LIMIT_MAX`) for tests.
- `mpm_test` is created by `infra/postgres-init/` on the volume's first start. If the volume already existed:
  `docker exec mpm-postgres-1 createdb -U mpm mpm_test`, then `db:migrate:test`.
- Host ports are **5434 / 6381**: 5432 / 6379 can be taken by a native or WSL Postgres/Redis, and 5433 / 6380 by the
  textile project's containers (`tsm-postgres-1`, `tsm-redis-1`), so both projects run side by side.

After editing `packages/shared-types`, run `pnpm --filter @mpm/shared-types build` (or `dev` for watch) — consumers read its `dist/`.

## Architecture

**Layered backend (routes → services → data):**
- `routes/` — validate input with Zod, call a service, return `{ data }`. **No business logic.**
- `services/` — all business logic; talks to the DB via Drizzle and to external APIs.
- `plugins/` — cross-cutting: JWT auth (`requireUser`, `requireAdmin`, `requireAdminRole(...)`), DB, Redis, rate limiting, central error handler.

**State machines are the product.** Listing status (F2), offer status (F6), deal status and rental booking status (F7),
and part request status (F8) are defined in `packages/shared-types`. Transitions live in one service each and are
enforced server-side; clients only display them.

**Left / Right / Pair (F3)** is a first-class listing and part-request field (`PART_SIDES`), not a free-text spec.
`complementarySide()` in shared-types is the one definition of "the other side"; matching and "show complementary
parts" use it.

**Part requests (F8)** are matched against newly published listings by a background job (category, part name,
side, brand/model compatibility, location), and the buyer is notified (F9). Matching never spams: cap the number of
notifications per request.

**Real-time:** emit to rooms from services via `fastify.io.of('/user' | '/admin').to(room)`, using the helpers in
`socket/rooms.ts` (never hand-typed room strings). Event names are `<domain>:<event>` (`offer:received`,
`deal:updated`); clients match by prefix.

**Background jobs:** add a `JobSpec` to `src/jobs/index.ts`. Jobs start only from `index.ts` (never `buildApp`, so tests
don't run them) unless `JOBS_ENABLED=false`. Each job's queries use `FOR UPDATE SKIP LOCKED`.

**Observability:** Sentry is opt-in via `SENTRY_DSN` (API) / `EXPO_PUBLIC_SENTRY_DSN` (app); only unexpected 500s are
reported, with PII keys redacted. Product analytics is PostHog in the app — see `apps/user-app/CLAUDE.md`.

**Money:** integer paise everywhere; convert input with `lib/money.ts` (`moneyStringToPaise`), never floats.

**Specs as JSONB** validated against each category's field template (managed in admin, A4), so a new category,
machine type or listing field needs no schema change or app release.

**Distance via PostGIS** `geography` (`ST_DWithin`, `ST_Distance`) — never compute distance in application code.
`businesses.location` is `geography(Point,4326)`; listings get their own point when they land.

**Admin RBAC:** roles `super_admin`, `moderator`, `verification_officer`, `category_manager`, `operations`, `support`.
`super_admin` passes every check. The API enforces it (`requireAdminRole`); the admin nav mirrors it (`lib/nav.ts`
`roles`). Every admin mutation writes `audit_log` (who, what, before/after).

## Code Patterns

### Naming
- Files: `kebab-case` (`offer.service.ts`, `use-listing.ts`); React Native components `PascalCase.tsx` in `components/`
- Types/interfaces: `PascalCase`; functions/variables: `camelCase`
- DB columns: `snake_case`; env vars: `SCREAMING_SNAKE_CASE`
- Redux slices: `camelCase` + `Slice` (`authSlice`)

### API response shape
```ts
{ data: T }                                          // success
{ error: string, code: string, details?: object }   // error
```

### API route prefixes
- `/auth/*` public · `/users/*` user JWT · `/listings/*`, `/enquiries/*`, `/offers/*`, `/deals/*`, `/part-requests/*`, `/rentals/*` user JWT · `/admin/*` admin JWT + role

### Errors
- Services throw `AppError` subclasses (`ValidationError`, `NotFoundError`, `ConflictError`, `ForbiddenError(message, code)`…) with a stable `code`.
- The central handler maps them; stack traces never reach clients.

### Database
- Drizzle for everything; raw SQL only for PostGIS spatial queries.
- Migrations in `infra/migrations/` — always `db:generate`, never hand-edit, never modify or delete an existing migration.
  Something Drizzle can't express (an extension, a trigger) goes in a `drizzle-kit generate --custom` migration.
- Phones stored E.164 (`+91XXXXXXXXXX`); money in paise (integer).

### Testing
- API: integration tests against a real local Postgres + Redis (no DB mocks). `buildApp({ infra: false })` for tests that must not touch infra.
- **A test run must leave the database exactly as it found it** — every suite deletes what it inserts in `afterAll`; fixtures unique per run (timestamped phones/slugs).
- Mobile: pure logic in `lib/` with co-located `*.test.ts`. Admin: Vitest + Testing Library (jsdom).

## Key Business Rules (from the scope)

1. One account can buy **and** sell (F1).
2. Login is asked only at the moment of intent (enquire, offer, sell, save) — guests can browse.
3. Every listing has: category/subcategory, part or machine name, specifications, quantity + unit, condition
   (New / Used / Unused / Excess), brand / model / compatible machines, side (Left / Right / Pair) where applicable,
   photos/video, price model (Fixed / Negotiable / Price on Request), location (F2).
4. Listings are previewed before publishing; sellers can edit, pause, remove, mark sold / unavailable, and mark
   machinery rented (F2, F7). Admins approve / reject, hide and remove (A3).
5. Offers: the seller can accept / reject / counter; both sides track offer status; an accepted offer becomes a deal
   with the agreed price and quantity (F6, F7).
6. A deal is recorded even when payment happens outside the platform (F7).
7. Part requests stay active until fulfilled or closed; new matching listings notify the buyer (F8).
8. Reviews only from parties to a completed deal (F7).
9. Suspended or blocked accounts can't sign in (`ACCOUNT_SUSPENDED`, A2).
10. Categories, machine types, brands, models, compatibility, units, conditions, side options and listing fields are
    admin-managed data (A4) — never hard-code a list the admin is meant to manage; the lists in shared-types are
    defaults and seeds.

## Development Workflow (Superpowers plugin)

The `superpowers@claude-plugins-official` plugin is enabled for this repo (`.claude/settings.json`). Use its skills for any non-trivial feature:

1. **Brainstorm → spec:** `superpowers:brainstorming` turns a scope module (e.g. "F3 left/right matching") into a design, saved to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`.
2. **Plan:** `superpowers:writing-plans` writes a step-by-step, checkbox plan to `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`.
3. **Build:** `superpowers:subagent-driven-development` (preferred) or `superpowers:executing-plans` implements the plan task by task, with review between tasks.
4. **Throughout:** `superpowers:test-driven-development` (red → green), `superpowers:systematic-debugging` for bugs, `superpowers:verification-before-completion` before claiming done.

Plans and specs are committed — they're the history of why the code looks the way it does.

**UI design skill:** `.claude/skills/frontend-design/` is Anthropic's `frontend-design` skill (copied unchanged from the
textile project). Use it for screens without an approved mockup. The project commands in `.claude/commands/`
(`/prime`, `/plan-feature`, `/execute`, `/create-prd`) remain available as a lighter-weight alternative.
